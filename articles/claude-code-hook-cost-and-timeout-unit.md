> 検証日: 2026-09-28（仕様を公式ドキュメントで再確認）／ Claude Code 2.1.270 ／ macOS 13.7.8

Claude Codeのフックは、何もせずに終わるスクリプトでも、呼ばれるたびにプロセスの起動分の時間を取ります。
またフック定義の `timeout` は秒で数えるので、ミリ秒のつもりで書くと1000倍の値になります。
どちらも設定ファイルを眺めるだけでは気づきにくく、数字を1つ測るか単位を1つ確かめれば見つかる種類の問題でした。

以下の数字と設定は、2026-09-07 に Claude Code v2.1.261、Intel Mac（macOS 13 Ventura）で行った環境の監査で得たものです。

## 何が起きたか

きっかけは、ツール呼び出しが体感で重いことでした。
ちょうど Claude Code の環境を監査していたので、原因を設定の側から探すことにしました。

そこで `~/.claude/settings.json` のフック定義を上から順に見直しました。
目についたのは、pixel-agents という連携ツールのスクリプト（node で動く `claude-hook.js`）が、11のイベントに登録されていたことです。
連携先のサーバはもう動かしておらず、登録だけが残っていました。

このスクリプトは連携先の設定ファイルを読み、ファイルが無ければすぐに `exit(0)` します。
そのファイルはもう存在しません。
つまり11件とも、毎回何もせずに終わっていました。
何もしないのだから時間もかからない、と私は考えていました。

同じ監査で、もう1つの設定も見つかりました。
別のプロジェクト（個人のObsidian vault）の `.claude/settings.json` で、UserPromptSubmit に登録したフックに `"timeout": 5000` と書いてありました。
書いたときの意図は5秒です。
同じファイルのグローバル側の定義は 5 と 10 で、こちらは正しく秒で書けていました。
取り違えていたのはこの1か所だけでした。

## どう測ったか

1件目は、フックのスクリプトが動く前に必ず払う時間、つまり実行系の起動時間を測りました。
各コマンドを20回ずつ走らせ、`time` の real 値を平均しています。
測った環境は Intel Mac、macOS 13 Ventura、node v22.14.0 です。

| 実行系 | 1回あたり |
|---|---|
| `node -e 0` | 100.8 ms |
| `python3 -c pass` | 80.6 ms |
| `bash -c :` | 17.2 ms |
| `jq -n 1` | 14.8 ms |
| `awk 'BEGIN{}'` | 7.9 ms |

node の起動だけで約100msかかります。
スクリプトの中身が `exit(0)` だけでも、この時間は減りません。

次に、登録のされ方を確かめました。
pixel-agents のスクリプトは PreToolUse と PostToolUse の両方に登録され、どちらにも `"async": true` が付いていませんでした。
非同期の指定が無いフックは同期で実行されます。
したがってツール呼び出し1回につき、node の起動が前後に1回ずつ、直列で2回入ります。

100.8ms を2回で約200msです。
ツールを100回呼ぶセッションなら、約20秒がまるごと待ち時間になる計算です。
この20秒は起動時間からの見積もりで、セッション全体の遅れを直接測った値ではありません。

2件目の timeout は、公式ドキュメント（https://code.claude.com/docs/en/hooks ）で単位と既定値を確かめました。
単位は秒です。
既定値はコマンドを実行するフックで600秒ですが、UserPromptSubmit など一部のイベントでは30秒に引き下げられます。

既存の設定の点検には、次のコマンドを使いました。

```
command grep -rn '"timeout"' ~/.claude/settings.json */.claude/settings.json
```

## 原因

1件目の原因は、フックが「何をするか」ではなく「起動されること」自体に時間がかかる点にあります。
Claude Code はフックのたびに新しいプロセスを立ち上げるので、中身が空でも実行系の起動時間は毎回かかります。
node と python3 は起動の時点で一段重く、bash や jq、awk とは桁が1つ違いました。

そこに、登録の仕方が掛け算で効きました。
PreToolUse と PostToolUse は、ツール呼び出しのたびに発火するイベントです。
両方に同期で登録すると、ツール1回あたりの待ちが2倍になります。
逆に SessionStart や Stop のように発火が少ないイベントなら、同じ100msでもほとんど問題になりません。
重さを決めていたのは、スクリプトの中身よりも、起動の重さと発火の回数の組み合わせでした。

2件目の原因は、同じ `timeout` という名前が、場所によって違う単位を持っていることです。
フック定義の `timeout` は秒です。
一方で、Claude Code の Bash ツールに渡す `timeout` はミリ秒で、既定は120000、最大は600000です。
Bash ツールの値を見慣れていると、フックにもミリ秒の感覚で4桁の値を書きやすくなります。
その結果、5秒のつもりの `5000` は5000秒、約83分になりました。

UserPromptSubmit の既定は30秒なので、5000秒はその166倍です。
このフックはプロンプトを送るたびに走ります。
スクリプトが途中で止まった場合、送信のたびに最大83分待たされ得る状態でした。
実際に待たされたわけではなく、設定を読んで見つけた潜在的な問題です。

## どう直したか（直せなかったか）

pixel-agents のフックは11件すべて削除しました。
連携先のサーバは動いておらず、全件が空振りだったからです。

削除にしたのは、フックを1件ずつ止めるフラグが無いためです。
`disableAllHooks` で全体を止めることはできますが、それでは必要なフックまで止まります（https://code.claude.com/docs/en/hooks ）。
消す前に `settings.json.bak-YYYYMMDD` を作っておき、戻せるようにしました[^once]。

以後、Pre/PostToolUse に登録するフックは、次の順で判断しています。

1. 本当に毎回必要かを疑う
2. 必要なら、実行系を node や python3 から bash、jq、awk に寄せる
3. 結果を待つ必要がないなら `"async": true` を付ける
4. 使っていない連携は、エントリ自体を消す

ただし、上の起動時間の絶対値はこのMacで測ったものです。
機種が変われば値は変わります。
それでも、node と python3 が一段重いという順序は動きにくいと見ています。

timeout については、フックの `timeout` は必ず1桁か2桁の秒数で書くと決めました[^sessionend]。
3桁以上の値を見たら、ミリ秒との取り違えを先に疑います。

## 残っている疑問

1件目で測ったのは実行系の起動時間までです。
フックを消した前後で、ツール呼び出し1回の待ちが実際に何ms縮んだかは測っていません。
Claude Code がフックを起動する際に、実行系の起動以外の上乗せがあるのかも確かめていません。
同じ環境で試すなら、フックの有無だけを変えて、同じツール呼び出しを繰り返した時間を比べるのが手早いと思います。

2件目については、timeout に達したフックがどう扱われるのか、つまり送信が止まるのか、フックだけ打ち切って先に進むのかを、実際に止めて確かめてはいません。
スクリプトの冒頭に長い `sleep` を入れ、短い timeout を付けて1回送ってみれば挙動が分かります。

体感の重さを追って見つかったのは、放置していた11件の空振りでした。
あの重さのうち、どれだけがこの11件の分だったのかは、まだ分かっていません。
それでも、設定ファイルの中身が正しいかだけでなく、何回起動されるかまで数えておけば、同じ種類の引っかかりには早く気づけます。

[^once]: 「1回だけ動かす」指定の `once: true` で軽くする手も考えられますが、この指定はスキルの frontmatter でしか効かず、`settings.json` とエージェントの frontmatter では無視されます（https://code.claude.com/docs/en/hooks ）。
[^sessionend]: SessionEnd のフックだけは全体で1.5秒の予算を共有し、個別に長い `timeout` を書くと予算がその値まで（最大60秒）引き上げられるので、セッションの終了がその分待たされ得ます（https://code.claude.com/docs/en/hooks 、2026-09-28 に確認）。
