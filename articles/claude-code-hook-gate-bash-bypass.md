> 観測日: 2026-09-08、2026-09-10、2026-09-11、2026-09-12、2026-09-18、2026-09-28 ／ 記事の作成: 2026-10-22（Claude Code 2.1.270、macOS 13.7.8）

Claude Code のフックで `Edit|Write` にだけゲートを掛けると、同じファイルを Bash から書き換える道が開いたまま残ります。
私はその穴を、Bash のコマンド文字列を照合する自作のフックで塞いだつもりでした。
実際には、`ln` や `touch` は判定にも掛からずに通り、読むだけのコマンドのほうが止められていました。

## 何が起きたか

2026-09-08 は、~/.claude を守るゲートを整備していた日です。
ゲートは plan-gate、wfa-gate、grill-gate、knowledge-inbox-gate の4本で、~/.claude 配下のファイルを承認なしに書き換えさせないためのフックです。

ところが、Bash の heredoc や `mv` で CLAUDE.md を書き換えると、ゲートは1本も起動しませんでした。

この穴を塞ぐのは、Bash の呼び出しを検査する自作のフック `bash-guard.sh` の3節です。
3節は、~/.claude への書き込みを、コマンド文字列の照合で検出します。

逆の向きのずれもありました。
2026-09-10 には、`2>/dev/null` を付けただけの読み取りのコマンドが止められました。
2026-09-11 には、knowledge/ でのコミットが止められています。
ファイルを書き換えるコマンドが通り、読むだけのコマンドが止まっていたことになります。

## どう測ったか

2026-09-12 に、フックへコマンド文字列を直接渡して、判定だけを見ました。
`CLAUDE_NO_JUDGE=1` を付け、コマンド自体は実行していません。

| 判定 | コマンド |
|---|---|
| deny | `mv ~/.claude/skills/foo ~/.claude/skills-archive/` |
| deny | `jq -r '.a' ~/.claude/settings.json \| grep -c '>'`（引用符内の `>`） |
| 通過（判定とバックアップを経由） | `rm -rf ~/.claude/skills/foo`、`rm ~/.claude/settings.json` |
| 通過（判定も経由しない） | `ln -sf /tmp/x ~/.claude/CLAUDE.md`、`rsync -a /tmp/x/ ~/.claude/skills/`、`touch ~/.claude/CLAUDE.md` |

戻せる退避の `mv` と読むだけの `jq` が止まり、CLAUDE.md に向けた `ln -sf` と `touch` は判定すら経由しませんでした。

誤検知のほうは、3節の正規表現を `[[ =~ ]]` で試して差を見ました。

```
commit -m "Co-Authored-By: Claude <noreply@anthropic.com>"  → 一致
commit -m "Weekly snapshot 2026-09-18"                      → 不一致
```

帰属表示を付けただけで、コミットが書き込み扱いになっていました。

2026-09-28 には、止められた同じコマンドを、cwd を変えて bash-guard に流しました。

- `ls -di //usr//bin/. /usr/bin; python3 -c '…'` は、cwd が ~/.claude/hooks なら deny。cwd がホームディレクトリと scratchpad なら通った
- `printf '%s -> %s\n'` を含むコマンドは、cwd がホームディレクトリでも deny。`->` を `=` に変えると通った

この日は5回止められ、1回が printf の書式の `->`、残り4回が `python3 -c` でした。
4回のうち2回は、コマンドが ~/.claude に触れておらず、私自身の `cd` で cwd が ~/.claude/hooks に残っていただけです。

## 原因

素通りの原因と誤検知の原因は、別々にあります。

素通りのほうは、ゲートの起動条件から来ていました。
4本のゲートは settings.json の matcher が `Edit|Write`（一部は `NotebookEdit` と `ExitPlanMode`）です。
matcher はツール名で起動するフックを選ぶので、Bash のツール呼び出しではゲートが1本も起動しません。

その穴を受け持つ3節も、書き込みを検出する語が限られていました。
見ているのは、`>`（`2>/dev/null` などは除いてから見る）、`sed -i`、`tee`、`mv`、`cp`、`python3 -` などのインタプリタです。
`ln` と `rsync` と `touch` はこの中に無いので、書き込みとして拾われません。

さらに3節は、knowledge 配下だけを触る書き込みを丸ごと免除しています。
そのため knowledge 配下への Bash の書き込みは、knowledge-inbox-gate の代わりの検査も受けずに通るはずです。
これはコードを読んで確かめただけで、実行はしていません。

誤検知のほうは、`>` を探す正規表現をコマンド文字列全体に掛けていることから来ていました。

```
>>?[[:space:]]*[^|&[:space:]]
```

この式はリダイレクトかどうかを区別しないので、引用符の中の `>` にも、`->` にも、`<noreply@…>` の `>` にも当たります。
コマンドが ~/.claude を含むか、cwd が ~/.claude 配下なら、当たった時点で deny です。

インタプリタの判定は `(python3?|node|perl|ruby)[[:space:]]+-` です。
`python3 -c` のように `-` で始まる引数を渡すと、書き先を読めないので止めます。

cwd の扱いも誤検知を増やしていました。
フックが見る cwd は、コマンドを実行する前のセッションの cwd です。
Bash ツールは `cd` の結果を次の呼び出しに持ち越すので、一度 `cd ~/.claude/…` すると、以後の `python3 -c` は ~/.claude と無関係でも deny されます。

## どう直したか（直せなかったか）

誤検知は、3節が照合する前に、無害な部分を文字列から除く形で減らしました。

- `2>/dev/null` のような無害なリダイレクトを除いてから照合する
- 2026-09-19 に、除く処理に `s#<[^<>[:space:]]*>##g` を足し、山かっこで閉じたトークンを除く。帰属表示付きのコミットと、`<command-name>` を含む検索パターンが通るようになった

素通りのほうは、2026-09-12 に一部だけ塞ぎました。
plan-gate が開いている間（プランの承認の後と「プラン不要」の後）は、3節を通し、判定サブエージェントとバックアップを必ず経由させます。
ゲートが閉じている間の `ln` `rsync` `touch` の検出漏れは、残ったままです。
塞ぐなら、3節の検出語に足すことになります。

残っている誤検知は3つです。

- 閉じていない半角の `>` が文字列の中にあるとき（例: `grep "a > b" ~/.claude/…`）
- `python3 -c` や `node -` のように、インタプリタに `-` 付きの引数を渡すとき
- ~/.claude 配下を `cp` や heredoc で読むだけのとき（2026-09-18 に観測）

避け方は、コマンドの書き方の側にあります。
読むだけのスクリプトはファイルに置き、`python3 <パス>` で呼びます。
~/.claude を読むときは `cd` を使わず、絶対パスで書きます。
`grep` のように直接読める手段があれば、そちらを使います。
2026-09-12 に検索パターンの山かっこで2回止められたときは、括弧を `.{1,4}` に置き換えて通しました。

この手の限界は、文字列で照合するという作りそのものにあります。
Bash 側を文字列の照合で塞ぐ限り、動詞の列挙漏れと、引用符の中の誤検知は両方残ります。

## 残っている疑問

knowledge 配下への書き込みが Bash から素通りすることは、コードを読んで確かめただけです。
同じ形のゲートを持つ環境なら、フックへコマンド文字列を渡して判定だけを見る方法で、実行せずに確かめられます。

`Edit|Write` にだけゲートを掛けている環境なら、どこでも同じ穴が開くと考えています。
私が踏んだのは自作の4本だけなので、これは推測です。
ゲートを書いたら、`ln -sf` と `touch` を守りたいファイルに向けて、判定だけを見てみるのが早いと思います。
