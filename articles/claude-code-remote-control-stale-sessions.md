> 観測日: 2026-08-21 ／ 記事の作成: 2026-11-05（Claude Code 2.1.270、macOS 13.7.8）

Claude のデスクトップアプリのサイドバーに、開いた覚えのない空のセッションが数十件規模で並んだことがあります。
症状は、Remote Control 機能の既知のバグとして GitHub に報告されているものと一致しました。
`~/.claude/session-env/` に、終わったセッションのメタデータが残り続けていて、私の環境では2632件たまっていました。
最初に原因だと結論した自作の定期実行は、実測すると無関係でした。

## 何が起きたか

2026-08-21 に Claude のデスクトップアプリを開くと、サイドバーの「グループなし」に見覚えのないセッションが並んでいました。
サイドバーには、自分で開いた会話だけが並ぶものだと思っていました。
数は数十件規模です。
名前はどれも `<ホスト名>-<形容詞>-<名詞>` の形で、ホスト名のあとにランダムな2単語が付いていました。

1つ開いて中身を確かめると、claude-mem プラグインの初回起動のメッセージ（`This project has no memory yet`）しか表示されませんでした。
実質的に空のセッションです。

自分で始めた会話なら、名前か中身のどちらかに覚えがあるはずです。
どちらにも覚えがない以上、私の知らないところで何かがセッションを作っている。
そう考えて、当初は自分で組んだ定期実行の仕組みが原因だと結論しました。

その仕組みは、Claude の使用量をメニューバーに出すために自作したアプリの一部です。
LaunchAgent から15分ごとにシェルスクリプトを動かし、そのスクリプトが `claude` を PTY で起動します。
15分ごとに起動するのだから、起動のたびに新しいセッションができて、それがサイドバーに並んでいるに違いない。
この結論は、スクリプトのコードを読んだだけで出していました。

## どう測ったか

この見立ては、実測で否定されました。
~/.claude で開いたセッションの記録は、`~/.claude/projects/` の下の1つのフォルダにたまります。
そのフォルダにある実セッション838件のうち、834件に「.」という1文字のメッセージの痕跡がありました。

「.」は、定期実行が statusLine を発火させるために送る文字です。
痕跡が838件中834件にあるということは、定期実行は新しいセッションを作っていません。
既存の最新セッションに追記していただけでした。

では、サイドバーに並んだセッションの実体はどこにあるのか。
次に、会話の記録が置かれる場所を2つ探しました。

1つ目は、CLI の会話履歴を置く `~/.claude/projects/` です。
全34プロジェクトのフォルダを確かめましたが、該当するセッションはありませんでした。

2つ目は、デスクトップアプリのローカルのセッション置き場（`~/Library/Application Support/Claude/claude-code-sessions/`）です。
ここには33件しかなく、該当するものはありませんでした。

サイドバーには出ているのに、会話の記録はどちらの場所にもありません。
自分の仕組みを疑う線が消えたので、GitHub の issue を検索しました。
そこで、症状の一致する既知のバグが見つかりました。

## 原因

見つかった issue は [anthropics/claude-code#31487](https://github.com/anthropics/claude-code/issues/31487) です。
題名は「Remote control: app shows stale sessions and does not display currently active session」でした。
重複の issue としてクローズされていて、根本の修正が入ったかは確かめていません。

仕組みは2段に分かれます。

1段目は、セッションのメタデータが消えないことです。
CLI のセッションを起動すると、`~/.claude/session-env/` に UUID ごとのサブディレクトリが作られます。
これがセッションを終えた後も削除されず、たまり続けます。
私の環境では2632件たまっていました。
issue の報告者の環境では1097件です。

2段目は、Remote Control がそのたまったデータを見ることです。
私の環境では、`bridge-state.json` で Remote Control が `enabled: true` になっていました。
Remote Control は、たまったデータから古い、実体のないセッションを拾い、サイドバーに新しいセッションとして表示してしまいます。

この2段で、測った結果とも辻褄が合います。
サイドバーのセッションの会話の記録が `~/.claude/projects/` にもデスクトップアプリの置き場にもなかったのは、実体のないセッションだったからです。

当初の見立てが外れたのは、コードを読んだだけで、実測せずに結論を出したからでした。

## どう直したか（直せなかったか）

対処はまだしていません。

issue のコメントでは、一般的な回避策として次のコマンドが挙がっています。

```bash
rm -rf ~/.claude/session-env/
```

このコマンドは、`~/.claude/session-env/` をフォルダごと削除します。
ただ、これが公式の修正としてリリースされたものかは確かめていません。
実行する場合は、CLI のセッションをすべて終了してから行うのが安全だと考えています。
この考えも検証していません。

この症状が出るのは、Remote Control を有効にした状態で Claude Code の CLI を日常的に使っている場合です。
会話履歴が数百件から数千件ある使い方ほど、session-env にはメタデータがたまりやすくなります。

## 残っている疑問

1つ目は、根本の修正が入ったかどうかです。
issue が重複としてクローズされた後に、根本の修正が入ったのかは確かめていません。
自分の環境で session-env がまだ増え続けているかを見れば、修正の有無の手がかりになります。

2つ目は、回避策のコマンドの効き目と安全性です。
session-env を消せばサイドバーの空のセッションが消えるのか、消した後に CLI のセッションに不具合が出ないのかは、試していないので分かりません。

3つ目は、数の差です。
サイドバーに並んだのは数十件規模で、session-env にたまっていたのは2632件でした。
2632件のうち、どれがサイドバーに出て、どれが出ないのかは確かめていません。
Remote Control を無効にすればサイドバーに出なくなるのかも、試していません。

同じ症状に当たった読者は、`~/.claude/session-env/` の下のサブディレクトリの数と、Remote Control が有効かどうかを見ると、この記事の症状と同じものかを見分けやすくなります。
