> 観測日: 2026-08-20、2026-09-07 ／ 記事の作成: 2026-11-27（Claude Code 2.1.270、macOS 13.7.8）

この記事で分かること

- 設定したフックが一度も動いていなかったことを、痕跡から確かめる方法
- フックにツールの入力を渡す環境変数は無く、stdin の JSON で受け取ること
- Read ツールが拡張子で弾くファイルでは、フックがそもそも呼ばれないこと

対象の読者: Claude Code のフックを書いたものの、本当に効いているのか自信がない人

Claude Code のフックは、壊れていてもエラーを出さないことがあります。
私の環境では、設定したフックが1件もコミットを作らないまま、未コミットの変更が50件たまっていました。
別の場面では、作ったフックがそもそも呼ばれていませんでした。
どちらも、フックが走れば残るはずの痕跡を見ることで、動いていないと確かめられました。

## 設定されているのに1件もコミットしていなかったフック

2026-09-07、Claude Code の環境を見直していて、あるプロジェクトの `.claude/settings.json` に次のフックを見つけました。
変更を git に自動でコミットするためのフックです（スクリプト名は伏せています）。

```json
".claude/hooks/<自動コミットのスクリプト>.sh \"$TOOL_INPUT_FILE_PATH\""
```

このフックは 2026-07-30 に設置されていました。
設定どおりなら、フックが走るたびにコミットが増えるはずです。

ところが、設置以来、フックが作ったコミットは1件もありませんでした。
未コミットの変更は50件たまっていました。

## フックが走ったかを痕跡で確かめる

フックが走ったかどうかは、スクリプトが最初に残す副作用から逆算すると確かめられます。
このスクリプトは、`git add .` を条件なしに実行してから commit します。
そこで、次の2つを数えました。

```bash
git reflog | wc -l                      # → 1（初回コミットのみ）
git diff --cached --name-only | wc -l   # → 0
```

reflog は1行で、初回のコミットしかありません。
ステージされたファイルも0件です。
ステージが空なので、スクリプトは `git add .` に到達していないと言い切れました。

## フックに渡る入力は stdin の JSON だけ

公式ドキュメント（https://code.claude.com/docs/en/hooks）で確かめると、2つの誤りが重なっていました。
確認したのは 2026-09-07 時点の v2.1.261 です。

1つ目は、`TOOL_INPUT_FILE_PATH` という環境変数が存在しないことです。
フックがツールの入力を受け取る経路は、stdin に流れてくる JSON だけです。
JSON には `tool_name`、`tool_input`、`cwd`、`session_id` などが入っていて、bash なら `jq -r '.tool_input.file_path'` で編集したファイルのパスを取れます。
公式が定義している環境変数の中に、ツールの入力を渡すものはありません[^env]。

この誤りは、壊れていても気づけません。
シェルは未定義の変数を空文字に展開するだけで、エラーを出さないからです。
設定ファイルを読んだだけでは、引数が空で渡っていることは見えません。

2つ目は、コマンドを相対パスで書いていたことです。
フックは、その時点の作業ディレクトリで走ります。
セッション中に `cd` が走れば、作業ディレクトリは変わります。
ディレクトリが消えていれば、セッション開始ディレクトリ、プロジェクトルート、ホーム、システムの temp の順に、生き残っている最初の場所へフォールバックします。
そのため、コマンドの相対パスは信用できません。

## 環境変数と相対パスの直し方

このフックは、フックごと撤去しました。
同じことをするフックを書き直すなら、次の2点を押さえるのがおすすめです。

- ツールの入力は、環境変数ではなく stdin の JSON から `jq` で取り出す
- コマンドは、公式が勧める `${CLAUDE_PROJECT_DIR}/.claude/hooks/<スクリプト>.sh` の形で書く

設定の `env` ブロックに書いた変数は、フックにも届くはずです[^envblock]。

## Read ツールでは呼ばれないフック

フックが黙って効かなかった例は、もう1つあります。
2026-08-20、Officeファイルを Read しようとしたら変換ツール（markitdown）へ誘導するフックを作りました。
`.docx` を Read すると、次のエラーが返ります。

```
This tool cannot read binary files. The file appears to be a binary .docx file.
```

このとき、PreToolUse(Read) のフックも、PostToolUseFailure(Read) のフックも実行されませんでした。
確かめ方は単純で、フックスクリプトの先頭に次の1行を仕込みました。

```bash
echo "$(date) fired" >> /tmp/claude-hook-check.txt
```

`.docx` を Read しても、このファイルには何も記録されませんでした。
`.md` を Read すると、記録されました。

原因は、Read ツールの拡張子によるバイナリ判定が、フックを呼ぶより前の入力検証の段で走っていることです。
中身がテキストでも、拡張子だけで拒否されます。
`printf 'dummy' > a.docx` で作ったファイルでも、同じエラーになりました。
入力検証で止まった操作にはフックが呼ばれないので、フックでは捕まえられません。

対処として、Officeファイルの扱いはフックにせず、CLAUDE.md の指示で担保することにしました。
PDF は Read が対応している形式なのでフックが発火し、`permissionDecision: "ask"` で誘導できます。

## まとめ

2つの例に共通していたのは、フックが効いていないことをエラーが教えてくれなかったことです。

- 環境変数の例：未定義の変数が空文字に展開され、エラーにならなかった
- Read の例：フックより前の入力検証で止まり、フックが呼ばれなかった

フックを書いたら、先頭に日時を追記する1行を仕込み、狙った操作で記録が増えるかを先に見るのがおすすめです。
私の環境では、この1行で、誘導のフックが `.docx` では呼ばれないことが分かりました。
すでに動かしているフックなら、スクリプトが最初に残す副作用（今回は git のステージ）を数えると、走っていたかを後からでも確かめられます。

[^env]: 公式が挙げている環境変数には `CLAUDE_PROJECT_DIR`、`CLAUDE_PLUGIN_ROOT`、`CLAUDE_PLUGIN_DATA`、`CLAUDE_EFFORT`、`CLAUDE_CODE_REMOTE`、`CLAUDE_CODE_BRIDGE_SESSION_ID` などがあり、どれもツールの入力は渡しません。
[^envblock]: 公式には、`env` ブロックはすべてのセッションとそのサブプロセスに適用されると書かれています。ただ、今回のフックで設定の変数が届いていたかは切り分けきれていません。
