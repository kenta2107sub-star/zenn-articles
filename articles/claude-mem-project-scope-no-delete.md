> 観測日: 2026-09-07 ／ 記事の作成: 2026-11-13（Claude Code 2.1.270、macOS 13.7.8）

Claude Code に claude-mem プラグインを入れて使い続けると、観測（claude-mem が記憶として DB にためる記録）がたまっていきます。
私の環境では2,903件たまり、そのうち67%が、フォルダごと削除したプロジェクトのものでした。
消そうとして調べた結果、整理してもセッションに載る記憶は変わらず、削除の手段も用意されていないことが分かり、手を止めました。
同じように古い記憶を消したくなったときに、何を確かめれば整理の要否を決められるかを書きます。

## 何が起きたか

2026-09-07 に Claude Code の環境を見直していて、claude-mem の DB の中身を数えました。
観測は2,903件ありました。
そのうち67%は、もうフォルダごと削除したプロジェクトの観測です。

claude-mem は、セッションの開始時に過去の観測をコンテキストに載せます。
消えたプロジェクトの観測が67%を占めているなら、今の作業と関係のない記憶がセッションに混ざり、注入のノイズになっているに違いない。
そう考えて、DB の整理に取りかかりかけました。

狙いは単純で、削除済みのプロジェクトの観測を消せば、残った観測だけが載るようになるはずでした。
件数が減れば、ディスクも空きます。

ところが、消す前に注入の範囲を確かめると、この前提が成り立っていませんでした。
消えたプロジェクトの観測は、今のプロジェクトのセッションには、もともと載っていなかったのです。

## どう測ったか

最初に確かめたのは、セッションに載る観測の範囲です。
別フォルダ（スクラッチ作業フォルダ）でセッションを開きました。
claude-mem は `This project has no memory yet` と返しました。

DB には2,903件の観測があります。
それでも、このフォルダのセッションには1件も載りませんでした。
DB 全体から観測を選んで載せる仕組みなら、どのフォルダで開いても、何かしらの観測が載っていたはずです。
注入される観測は、DB 全体ではなく、そのプロジェクトのものだけということになります。

次に、整理しようとしていた DB の規模を、SQLite を読むだけで確かめました。

```bash
sqlite3 ~/.claude-mem/claude-mem.db "select project, count(*) from observations group by 1 order by 2 desc"
```

プロジェクトごとの観測の件数が、多い順に並びます。
読むだけなので、DB を変えずに規模をつかめます。

ディスクの使用量も見ました。
この時点で `~/.claude-mem` は182MBで、そのうち chroma（ベクトルストア）が120MBでした。

最後に、削除の手段を探しました。
`package.json` の `bin` は null でした。
確認できたサブコマンドは `server` と `memory worker` 系だけで、観測を消すコマンドは見つかりませんでした。

## 原因

整理してもノイズが減らない理由は、注入がプロジェクト単位だからです。
SessionStart で載るのは、そのプロジェクトの観測だけです。
消えたプロジェクトの観測は、稼働中のプロジェクトのセッションには入っていません。
最初に立てた「注入のノイズになっている」という見立ては、この仕組みを確かめずに出していました。

では、整理して得られるものは何か。
調べた範囲では、次の2つだけでした。

- 横断検索（`mem-search` など）の結果に、消えたプロジェクトの観測が出てこなくなる
- ディスクが数十MB空く

一方で、整理には残るリスクが3つありました。

1つ目は、削除用のコマンドが無いことです。
消すなら SQLite を直接触るしかありません。

2つ目は、chroma との二重管理です。
chroma は全プロジェクト共通で、`~/.claude-mem/chroma-sync-state.json` の値はプロジェクトごとの累積ウォーターマークです。
この値は DB の実件数とは一致しません。
SQLite だけ消すと、chroma に孤児ベクトルが残ります。

3つ目は、worker が DB を開いたまま常駐していることです。
止めてからでないと、DB には触れません。

得られるものが検索結果とディスクだけなのに対して、手間とリスクは SQLite と chroma の両方にかかります。
整理が割に合わない理由は、この釣り合いにあります。

## どう直したか（直せなかったか）

整理はしませんでした。
DB が肥大しても注入の質は落ちないので、放置のコストはディスクだけです。
私の環境では、それが182MBでした。

規模が気になったときは、「どう測ったか」の節の `sqlite3` のコマンドで、読むだけの確認をします。
プロジェクトごとの件数が分かれば、どのプロジェクトの観測がたまっているかはつかめます。

この判断には条件があります。
確認したのは claude-mem 13.24.1（2026-09-07）です。
バージョンが上がって削除のコマンドが用意されれば、この判断は変わります。

もう1つ、DB とは別に気にしたのが料金の枠です。
`sdk_sessions.observed_billing` は、記録のある5件すべてが `pro` でした。
claude-mem の処理は Pro プランの枠を消費しています。
34日で `discovery_tokens` の合計は14,496,268でした。
2026-09-05 には `quota_exhausted` が記録されていて、枠を消費すること自体は確定しています。
ただ、この合計が課金対象のトークンと一致するかは確かめていません。

## 残っている疑問

1つ目は、`discovery_tokens` の意味です。
14,496,268が Pro プランの枠で数えられたトークンと一致するのかは、確かめていません。
`quota_exhausted` が記録された日の前後で、claude-mem の処理の量と枠の減り方を見比べる方法は考えられますが、私は試していません。

2つ目は、削除のコマンドがその後に用意されたかどうかです。
13.24.1 では見つかりませんでした。
新しいバージョンで `package.json` の `bin` とサブコマンドを見れば、確かめられます。

3つ目は、SQLite だけを消したときに、chroma に孤児ベクトルがどれだけ残るかです。
私は整理を中止したので、実際に消して残り方を見たわけではありません。
chroma 側を揃えて消す手順も、試していません。

同じように古い観測を消したくなった読者は、まず普段とは別のフォルダでセッションを開き、何が載るかを見てください。
`This project has no memory yet` と返るなら、私の環境と同じく注入はプロジェクト単位で、DB に何件たまっていても、別のプロジェクトの観測は載っていないと見てよさそうです。
